# Provider compatibility

Each supported provider/protocol pair has its own explicit upstream client. Each class implements one protocol, and thin subclasses share the protocol implementation. The shared Responses and Chat Completions clients ignore output extensions they do not model; a provider client validates only its own extensions. Prefer Responses when it supports the desired model and capabilities, then Messages, then Chat Completions. `molto.upstream.registry.CLIENTS` selects registered translation clients. Translated routes require a registered provider/endpoint pair; native routes permit every known provider with the requested protocol and let the SDK/server accept or reject the attempt. Neither path switches protocols.

Native attempts such as `Molto.messages(..., provider="openai", base_url="https://api.openai.com")` and `Molto.responses(..., provider="anthropic")` are allowed without claiming provider support. An unregistered native route uses the selected protocol SDK and the provider's credentials and default destination. Supply a protocol-specific `base_url` when needed: SDK resource paths are appended literally (Messages adds `/v1/messages`), and defaults for another protocol may not form a supported URL. Bedrock still requires an explicit regional destination.

## Selected protocols and configuration

| Provider | Client | Default SDK base URL | Credential |
| --- | --- | --- | --- |
| Together AI | `TogetherAIResponsesClient`, `TogetherAIChatCompletionsClient` | `https://api.together.ai/v1` | `TOGETHER_AI_API_KEY` |
| Fireworks | `FireworksResponsesClient`, `FireworksChatCompletionsClient` | `https://api.fireworks.ai/inference/v1` | `FIREWORKS_API_KEY` |
| OpenRouter | `OpenRouterResponsesClient` | `https://openrouter.ai/api/v1` | `OPENROUTER_API_KEY` |
| Bedrock | `BedrockResponsesClient`, `BedrockChatCompletionsClient` | Explicit regional URL required | `AWS_BEARER_TOKEN_BEDROCK` or `BEDROCK_API_KEY` |
| Gemini | `GeminiChatCompletionsClient` | `https://generativelanguage.googleapis.com/v1beta/openai` | `GEMINI_API_KEY` |

An explicit `api_key` overrides the configured provider key; registered hosted clients reject an empty key locally, while unregistered native attempts use the protocol SDK's authentication behavior. Missing provider keys cannot fall back to OpenAI credentials. An explicit `base_url` overrides the default without changing the provider or protocol. Authentication and account headers supplied through `extra_headers` cannot override the selected upstream identity.

Bedrock accepts either credential name from the environment or `.env`. `AWS_BEARER_TOKEN_BEDROCK` takes precedence when both names are configured, including across those sources. For the same name, the environment overrides `.env`.

Select the upstream protocol explicitly when it differs from the public method. For example, `Molto.chat_completions(..., provider="openrouter", endpoint="responses")` translates Chat input through the Responses client. The existing method defaults remain unchanged.

Protocol availability is documented by [Together](https://docs.together.ai/docs/inference/responses-api), [Fireworks](https://docs.fireworks.ai/api-reference/post-responses), [OpenRouter](https://openrouter.ai/docs/api_reference/responses/overview), [Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-responses-api.html), and [Gemini](https://ai.google.dev/gemini-api/docs/openai). Availability does not establish support for every model or feature. Together's Responses documentation lists GLM-5.2 and GLM-5.3 families; its Chat Completions recordings do not validate Responses for those Chat models. Together, Fireworks, and Bedrock expose separate Chat Completions clients to reach models and capabilities available through that protocol. Bedrock's [Chat Completions guide](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-chat-completions.html) documents the regional runtime and Mantle destinations; callers must choose a destination supported by their model.

## Provider differences

OpenRouter Responses identifies raw text and summaries explicitly. Its client accepts unsigned raw reasoning, including the recorded `format: "unknown"`, or summary output with an optional signature. Named formats, formatted summaries, mixed representations, and mid-item representation changes reject. Translated Responses history follows the same format rule: `format: "unknown"` on a raw-only item is accepted and omitted. Native passthrough preserves the original fields. Raw reasoning and unsigned summaries project to Chat and Messages; signed summaries can project to Messages. Chat `reasoning_content` and Messages `thinking` erase the raw-versus-summary label. On continuation, OpenRouter's summary profile interprets that unsigned history as a summary, which the Responses upstream builder rejects without a signature. This is a known limitation for both Chat and Messages reasoning-history replay, including raw text originally emitted by OpenRouter. Use native Responses history to retain the representation; output projection support does not establish a complete reasoning round trip.

Fireworks Responses uses the summary profile. Its recorded low-reasoning output contains unsigned summaries, which normalize and project to Chat or Messages. Responses and Messages upstream builders still reject replaying that summary history without a signature. Together uses the raw reasoning profile. The Bedrock and Fireworks Chat Completions recordings disable reasoning; they do not establish reasoning-enabled compatibility for those routes.

Gemini native Chat preserves opaque `extra_content.google` attachments on messages, content parts, and function calls, including nested nulls. Translated Gemini text and tool output extracts `extra_content.google.thought_signature` into a signature-only `Thinking` part immediately after the associated text or tool call. Responses exposes the token as reasoning `encrypted_content`; Messages exposes it as a thinking-block `signature`. Echoing those ordered output items as history restores the exact token to its original Gemini message or call. Text still streams immediately; a final-chunk signature follows its completed text part. A message signature without text is preserved when its attachment is unambiguous, including standalone and reasoning-only turns. A late message signature immediately following an unsigned tool call is rejected: the positional representation cannot distinguish it from that call's signature without changing or buffering the representation. The signature remains opaque and must stay with its issuing Gemini conversation.

Gemini uses the summary profile, matching Google's [thought-summary documentation](https://ai.google.dev/gemini-api/docs/openai). The recordings establish signature-only continuation, not reasoning-text translation. Other keys beside the signature are ignored on translated routes; a signature that is present but is not a non-empty string rejects. History that holds a second signature for the same message or call rejects. Message signatures without text are covered by synthetic tests only. Missing streamed tool indices are repaired only when the call identity is unambiguous; ambiguous output rejects rather than losing calls.

Gemini and Fireworks Chat clients omit `stream_options.include_obfuscation`, which their tested endpoints reject, on native and translated requests. Other streaming options remain intact. Gemini tool-bearing successful `finish_reason="stop"` becomes normalized tool termination on translated routes, producing Messages `stop_reason="tool_use"`; native output retains the provider's original finish reason.

When a translated Responses function tool omits `strict`, Molto currently sends non-strict tools. This differs from [native Responses](https://developers.openai.com/api/docs/guides/function-calling#strict-mode), which attempts strict schema normalization and may fall back for incompatible schemas. Set `strict` explicitly (`true` with a compatible schema, or `false`) when translating. Reproducing the provider's schema-normalization default is not implemented. Native passthrough preserves omission.

## Replay evidence

Provider conversations share `tests/upstream/test_multi_turn.py`. Cassettes use the existing scenario-first layout, for example `tests/cassettes/upstream_ir/tool_use/togetherai-responses-stream-00.yaml`. Each provider uses its own recordings. Canonical OpenAI/Anthropic fixtures are not reused as evidence of hosted-provider behavior.

The suite checks native SDK parity, actual-output history, normalized lifecycle and semantics, exact expected subsequent requests, and focused public translation or rejection cases. Independent SDK responses supply the comparison values. Expected normalized request copies account for documented wire representations and omitted optional metadata; recorded fixtures are not rewritten to match Molto output.

Bedrock captures use `https://bedrock-runtime.ap-southeast-1.amazonaws.com/openai/v1`, manual actual-output history, and zero retries. Responses requests use `store=false`; Chat Completions requests use `reasoning_effort="none"`. The model is an explicit system-defined inference profile. An earlier Mantle `openai.gpt-oss-20b` attempt returned HTTP 200 but stalled after `response.created` and `response.in_progress`; it was stopped after more than five minutes and remains in staging, outside the successful replay corpus. A Chat Completions attempt with `mistral.ministral-3-3b-instruct` returned an invalid-model HTTP 400 on runtime and timed out after 75 seconds on Mantle; neither attempt is successful replay evidence. The Singapore endpoint and global inference profile do not establish that inference occurred in Singapore.

Chat Completions continuation retains the actual SDK output. Together and Gemini repeat `delta.role`; the SDK accumulator concatenates these values, so the recording caller and replay helper restore the single `assistant` role before reuse. Fireworks rejects null output-only fields in assistant history, so its recording caller and replay helper omit those nulls. Gemini also rejects null optional message fields; its caller omits top-level nulls while retaining nested Google state unchanged. These are history-construction choices in the evidence workflow; native production output remains unchanged. The Fireworks and Gemini clients also omit null top-level message fields from every request they send, so history echoed from SDK output is accepted; nested values, including Google state, are unchanged. Every other client forwards message nulls as sent, which the Bedrock and Together recorded requests show those providers accept. Native parity sends input copies without empty output-only annotations, null `reasoning_content`/`tool_calls`, or stream-only tool indices, which are absent from the Chat request schema. The recorded source history is still checked against actual SDK output, and response bytes remain unchanged.

Gemini captures came from the [successful GitHub-hosted recording run](https://github.com/EmbeddedLLM/molto/actions/runs/42160882628), using the existing Actions secret, native OpenAI SDK calls through the recorder proxy, zero retries, and 90-second request deadlines. The temporary driver and workflow remain on a separate recording branch. Artifact YAML is imported unchanged. Streamed tool calls omit `index`; independent SDK references assign index zero only for these recorded single-call responses before comparison with the Gemini client. Native parity otherwise retains full provider output, including streamed `finish_reason="stop"` on tool calls and Google thought signatures on text and tool output.

The retained OpenRouter captures use an explicit free model, disabled provider fallbacks, zero price caps, and no plugins. Reported costs were zero. Responses history is manual with `store=false`. Captures establish only the recorded model, settings, and date; replay does not prove that translated request bodies were executed live.

## Opt-in live smoke checks

Replay verifies saved responses and request construction; it cannot establish that a hosted endpoint accepts today's translated requests. Run the standalone smoke command explicitly with one provider, model, and upstream protocol:

```bash
uv run --extra test python -m scripts.smoke_provider \
  --provider gemini --model gemini-3.1-flash-lite \
  --upstream chat/completions \
  --extra-body '{"reasoning_effort":"minimal"}'
```

The command uses configured provider credentials and makes live, potentially billable requests. It first checks Molto's native route, then the selected downstream protocols (all three by default), with text and a forced function call followed by its actual tool-result history in streaming and non-streaming modes. It checks tool identity, arguments, termination, and final output. The native route is a diagnostic control, not an independent SDK comparison; offline replay supplies SDK parity coverage.

Defaults bound the run to 18 HTTP attempts, 512 output tokens per request, a 45-second HTTP timeout, and a 180-second total deadline. SDK retries count against the HTTP budget. Use `--downstream`, `--mode`, `--max-requests`, and `--deadline` to narrow a run, and `--base-url` for an explicit protocol destination. Provider-specific `--extra-body` options cannot replace the smoke inputs, tools, modes, or token limits. Results report pass/fail and error class/status without printing provider response bodies or credentials. A failing check exits nonzero.

These checks create no cassettes and never run as part of pytest or default CI. A pass establishes only the selected model, settings, and scenarios at that time. Known unsupported reasoning/signature translations may fail; choose explicit reasoning controls where appropriate rather than treating all provider/model combinations as supported.
