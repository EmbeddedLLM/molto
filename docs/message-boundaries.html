Molto protocol investigation

Message boundaries across LLM protocols

How OpenAI Responses, Chat Completions, Anthropic Messages, Molto's normalized representation, and vLLM model renderers interpret messages, roles, parts, and turns.

Investigation snapshot: 2026-08-18

Executive summary

Molto preserves user-message boundaries and ordered text parts well on translated routes. It does not fully preserve system versus developer role identity, mid-sequence instruction placement when targeting Messages, enclosing assistant-message boundaries, Responses inner content-part boundaries, or multiple Chat choices.

Native routes are different. Same-protocol requests bypass the normalized representation, so the losses in this report primarily concern cross-protocol translation.

Under vLLM, accepting a role in an endpoint schema does not prove that the selected model understands it. The model renderer or chat template decides which boundaries and roles become model-visible tokens.

Three boundary layers

1. Wire messages

Request-array entries and their content parts or blocks.

2. Model-visible turns

The sequence remaining after provider rules and template rendering.

3. Streamed output

Generated items, blocks, choices, and deltas; not request turns.

Wire boundaries affect serialization and representability but do not guarantee independent model turns. Anthropic combines consecutive same-role Messages entries. vLLM may convert developer messages to system and move every system instruction to the beginning. Open-weight model chat templates can impose still different behavior.

Responses

Request and history

Responses accepts a string or an ordered list of heterogeneous input items. A string is shorthand for one user input. Message items can contain ordered text parts; reasoning and tools use separate item types. The pinned SDK and local Molto schema accept user, assistant, system, and developer messages without an alternation or first-message validator.

Molto keeps one user message as one UserInput and retains its ordered text parts. System and developer both become role-less SystemPrompt values. Multipart instructions are split, top-level instructions becomes indistinguishable from an input message, and assistant text parts become flat TextOutput values.

Streaming

Responses distinguishes an output item, an inner content part, and deltas within that part. Molto preserves one output item as one normalized part but does not retain inner content indexes. Projection recreates one inner part at index zero. It also assumes output-item lifecycles do not interleave.

Chat Completions

Request and history

Each messages[] element is a native message boundary. The official schema includes developer, system, user, assistant, tool, and legacy function messages and gives no positional restriction for system or developer. Newer OpenAI reasoning models prefer developer instructions over the older system mechanism.

Molto preserves user messages and their ordered text parts. System and developer both become SystemPrompt. Assistant reasoning and text survive only as adjacent normalized values; there is no enclosing assistant message. Tool-call-only assistant messages, non-text user parts, and multipart assistant content are unsupported on translated routes.

The local wrapper has a pinned-SDK schema gap: valid system or developer content-part arrays can validate but serialize as empty arrays because only user content replaces the SDK iterable with a concrete list.

Streaming

A stream is one assistant message per choice. Molto reads only choices[0]. Choice-zero text and reasoning deltas are retained, but Chat cannot reproduce normalized part-start and part-end boundaries. A source chunk containing both reasoning and text can become two projected chunks.

Anthropic Messages

Request and provider turns

A message contains a string or ordered content blocks. String content and one text block are documented equivalents. Anthropic combines consecutive user entries or consecutive assistant entries into one conversational turn, so preserving two wire objects does not preserve two model-visible turns. A final assistant entry is a response prefill.

Mid-conversation system messages

Messages has no developer role. On supported Anthropic models, a system message can appear mid-conversation, but it cannot be first, must follow a user message or qualifying server-tool result, must be last or followed by assistant, and cannot split a tool use from its result. Later system sections override earlier instructions for subsequent turns.

Molto's translated path currently turns every system message into a plain SystemPrompt, collects all such prompts from the entire history, joins them, and emits one top-level system value. This loses placement, priority, cache-prefix behavior, and individual instruction boundaries.

Assistant and stream boundaries

The Messages adapter flattens each assistant message into thinking and text parts. Target projection groups every adjacent assistant part into one assistant message, regardless of its original parent. Streaming preserves supported indexed text and thinking blocks, though generic non-empty content placed directly on a normalized part start is not reproduced.

vLLM: schema versus renderer

vLLM eventually constructs a renderer conversation for all three protocol families. Responses items may be regrouped into chat messages. Chat content parts remain structured in OpenAI content mode but can be joined with newlines in string mode. The Anthropic-compatible endpoint can extract and merge inline systems when a template requires system-first ordering.

The Hugging Face renderer has a developer fallback: if a developer message exists and the template does not explicitly support that role, developer is converted to system and all system messages are consolidated at position zero. This deliberately trades sequence fidelity for template compatibility.

Open-weight model specifics

Kimi K3

Kimi K3 uses a dedicated Python XTML renderer instead of generic Jinja. Structural markers encode the conversation. Tool-result messages can be reordered to match assistant tool-call order. System, user, and assistant structures are documented; an independent developer role is not.

Qwen

Qwen's ChatML format places explicit control tokens around every turn:

<|im_start|>{{role}}
{{content}}<|im_end|>

Qwen documents system, user, and assistant semantics. It does not document developer as an independent instruction level. Under vLLM, developer is generally converted to system for templates that do not explicitly support it, and some Qwen templates require the resulting system message first. Tool results are rendered as special user messages.

Muse Glimmer

Muse Glimmer's ATEM template has explicit system, user, tool, and assistant branches, but no developer branch. It renders supplied system messages at their sequence location and inserts a default leading system only when no system message exists. Each supplied system message also receives reasoning, tool-definition, and recipient metadata.

vLLM's preprocessing is expected to convert developer to system for this template, potentially moving and merging instructions. Applying the template directly without that fallback would omit developer messages because no branch handles them.

Architecture implications

ProviderCapabilities.thinking remains appropriate for raw-versus-summary reasoning. Boundary and role behavior is different because it depends on the model renderer as well as the provider.

  1. Retain system versus developer identity, grouping, and position in an instruction item.
  2. Represent an assistant message as a container of ordered thinking, text, and tool parts.
  3. Define explicit loss policy for multiple Chat choices and Responses inner content indexes.
  4. Model renderer capabilities such as instruction roles, ordering, developer fallback, and same-role merging.
These capabilities must not be inferred from base_url. endpoint selects the wire protocol, provider identifies the serving implementation, and the selected model renderer determines how the accepted conversation becomes tokens.

Test coverage and gaps

Existing tests cover user-message and ordered user-part preservation, ordinary single-choice streams, Responses output-item transitions, and Messages thinking followed by text blocks. Focused regressions are still missing for:

  • system versus developer round trips and mid-sequence placement;
  • multipart system or developer messages;
  • adjacent parts belonging to two assistant messages;
  • Responses inner content indexes and interleaved output items;
  • multiple Chat choices and instruction content-part serialization; and
  • model-template-specific vLLM role rewriting.
